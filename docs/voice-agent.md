# AssemblyAI Voice Agent integration

The Workers adapter connects to AssemblyAI’s Voice Agent API for transcription, turn detection and speech generation. With the default `LLM_PROVIDER=nebius`, the stored agent calls Nebius Token Factory using `nvidia/Nemotron-3_5-Lightning`, and independent intake extraction uses the same model. With `LLM_PROVIDER=assemblyai`, conversation uses AssemblyAI’s managed model and extraction uses its LLM Gateway.

Synthetic protocol tests cover edge cases. The historical 2026-09-29 fictional local browser run used Nebius and exercised live model access, finalized caller speech, evidence extraction, an agent response after caller speech and non-silent two-way nurse playback. The [redacted evidence](evidence/polished-live-voice-2026-09-29.json) records that run. It does not verify production reliability, physical-device audio or recording controls.

## Create the stored agent

Run `node scripts/setup-voice-agent.mjs` to inspect a redacted dry run. It does not read env files or make requests. The optional `--apply` command creates a resource only when explicitly run. Default Nebius mode requires `ASSEMBLYAI_API_KEY` and `NEBIUS_API_KEY` in the process environment; `LLM_PROVIDER=assemblyai` requires only `ASSEMBLYAI_API_KEY`.

Default Nebius creation stores the Nebius credential with AssemblyAI. Its payload contains one custom LLM entry with base URL `https://api.tokenfactory.nebius.com/v1`, the exact model ID, 24 kHz mono PCM input/output, no greeting, and an inert initial prompt. A per-call prompt and tools replace the initial configuration before mic audio can pass. AssemblyAI’s REST create-agent request uses the API key in `Authorization`; WebSocket authentication uses its documented Bearer form. [Create an agent](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/create-agent), [Custom LLM configuration](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/connect-your-own-llm).

For the optional AssemblyAI path, inspect `LLM_PROVIDER=assemblyai node scripts/setup-voice-agent.mjs --dry-run`, then use the same selection with `--apply` when ready to create the agent. This payload uses `llm: []`, 24 kHz PCM, no greeting, and no Nebius credential. Use a separate stored agent for a local provider switch so another environment's agent remains unchanged. Set realtime `LLM_PROVIDER=assemblyai`, the resulting `VOICE_AGENT_ID`, and its reviewed `VOICE_AGENT_VERSION`. Unknown provider values fail closed.

AssemblyAI extraction defaults to `qwen3.5-4b-32k-fast` through its LLM Gateway, using the same AssemblyAI key. Clear an old `EXTRACTION_MODEL` override or set it to that model. This hosted model does not support remote `response_format` JSON-schema enforcement: the complete schema is supplied in the prompt, and every result must pass local JSON parsing, Zod validation, and exact finalized-transcript evidence checks. A single repair retry is shared across schema and evidence failures. There is no fallback model or acceptance of unsupported facts. Confirm the account's Gateway model access and rate limit before selecting this path; the local development account returned a two-request-per-minute limit during the September 30 check, so local conversation and extraction were restored to Nebius.

The script prints only the created ID and next steps. It never prints the returned provider object or credential. An ambiguous response requires checking the provider dashboard before retrying, because another POST may create a duplicate. A creation response is not live verification. Record the agent ID and an operator-reviewed configuration revision; no provider version is inferred from an undocumented response field.

## Session protocol

`connectVoiceAgent(options, callbacks)` returns a Workers-native session with `send`, `requestReply`, `interrupt`, `update`, `close`, `ready` and `sessionId`. First it sends only `session.update.session.agent_id`. In the historical Nebius metadata probe, AssemblyAI first sent `session.updated` with the resolved stored configuration and no session ID, then `session.ready` with that configuration and the ID. The adapter validates the initial PCM formats, selected LLM configuration and absence of a greeting. Nebius requires the exact model/base URL; AssemblyAI managed mode requires an explicit empty `llm` array. It checks these without treating that first update as the mutable prompt/tools acknowledgment. On `session.ready`, it exposes the identity for durable cleanup, verifies the configuration again, then sends the mutable prompt/tools. Audio remains blocked until the subsequent `session.updated` confirms the expected prompt/tools and audio configuration. AssemblyAI may omit `additionalProperties: false` and add empty `required` arrays in the resolved tool JSON Schema; comparison tolerates those rewrites while the server still parses each tool call strictly. Other missing or mismatched echoes fail closed. A 10-second configuration deadline bounds an incomplete handshake. [Deployment](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/deploy), [WebSocket events](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/events-reference).

Input is raw PCM16 little-endian at 24 kHz, in real-time chunks of at most 100 ms; the caller uses 50 ms. Output is decoded from base64 with a one-second per-event cap. Odd trailing bytes are carried to the next chunk of the same reply; an incomplete sample at normal completion fails closed. No raw audio or resume credential is persisted by the adapter. Mic audio is never buffered before readiness. Session totals, text, tools and individual events have finite limits. [Audio contract](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/audio-format).

Final caller items and agent replies are deduplicated by their provider IDs. Every callback carries the provider session ID where relevant. User partial transcripts replace prior partial text. Tool reply IDs use the documented `fc-` prefix and never become playable agent replies. Tool callbacks execute without blocking receipt of `reply.done`; an omitted status means normal completion, while `status: "interrupted"` means barge-in. AssemblyAI requires `tool.result` only while the latest turn event is a completed `reply.done`. The adapter changes that idle state only on `reply.started`, `input.speech.started`, and `reply.done`; unrelated transcript and tool events leave it intact. It flushes all ready pending results at completion and again when asynchronous tools finish after completion. Speech start or a new reply holds pending results until the next completed reply, while an interrupted reply discards them. Duplicate call IDs execute once; reuse with different arguments fails. Tool exceptions are returned as generic errors, without provider or credential text. [Client tools](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/tools/client-side-tools).

`interrupt()` immediately gates output locally and drops pending audio bytes. Caller speech and interrupted reply events invalidate playback through the application callbacks. There is no invented provider cancel event. `close()` sends `session.end` and closes a known session. If closure occurs before its ID arrives, the adapter blocks all conversation activity and uses the remainder of the original 10-second handshake deadline to obtain the ID before ending it. On ownership changes the application closes the provider session. Audio messages in the documented API do not include a reply ID, so association relies on ordered WebSocket delivery between `reply.started` events. Explicit foreign IDs are rejected if supplied; arbitrary interleaving without IDs cannot be distinguished. NurseBridge does not automatically reconnect the provider; it requests nurse help. A new fictional call is needed for new automated intake.

## Recording, deletion and live activation

AssemblyAI documents automatic session recordings, transcripts and configuration history. Its current `DELETE /v1/sessions/{id}` operation returns 204 and soft-deletes the session, making it absent from listings and its artifacts inaccessible. `deleteVoiceAgentSession` implements that authenticated request, treating 404 as already absent, with bounded timeout and sanitized errors. The Durable Object owns durable retry scheduling. `session.end` is session termination, not deletion. [Session history and deletion](https://www.assemblyai.com/docs/voice-agents/voice-agent-api/session-history#delete-a-session).

The inspected documentation does not establish a recording-disable control, retention duration, or physical backup erasure guarantee. Provider recording/retention remains unverified; credentials, agent creation and logical deletion do not establish a retention guarantee. Hosted activation remains blocked by default. With explicit operator approval, set `BROWSER_LIVE_INTAKE_ORIGIN` to the single HTTPS origin in `ALLOWED_ORIGINS` to enable browser voice. This uses live providers with the existing caller recording consent and runtime model/tool validation. Health continues reporting recording retention, deletion and clinical readiness as unverified. This opt-in does not enable telephone intake. No real patient data is authorized by this setup documentation.

For a **fictional local compatibility test only**, set `FICTIONAL_LIVE_TEST=true` on the realtime Worker and `PROVIDER_MODE=live` on both Workers. Every entry in realtime `ALLOWED_ORIGINS` must be an exact `http://localhost`, `http://127.0.0.1` or `http://[::1]` origin, with an optional port. This bypasses only the recording-controls and voice-compatibility activation checks. It still requires the selected provider's credentials (both API keys for Nebius, only the AssemblyAI key for managed mode), a versioned stored agent, the app’s separate caller recording consent, and the normal authenticated session and socket flow. The health response continues to report provider verification, retention verification, and deletion verification as false. Do not enable this flag in a deployed Worker: the Origin allowlist is operator configuration, not proof that the Worker itself is running locally. The flag alone does not validate provider compatibility; the opt-in browser test measures the actual handshake and call outcome. The historical Nebius run on 2026-09-29 passed with one finalized caller turn, one evidence-linked fact, three assistant turns, and non-silent receiving worklets in both directions after takeover. Stale agent samples were zero and provider cleanup completed. See [test results](test-results.md#polished-voice-path-verified-with-live-providers-on-2026-09-29).

A connection can fail before the provider supplies a session ID. NurseBridge preserves a content-free attempt record (local attempt ID, agent ID, start time, reconciliation status) and reports that recording cleanup requires operator reconciliation. A restart also marks incomplete attempts for reconciliation. An operator must inspect the provider session history for the matching agent and time, establish identity, and apply the provider's deletion process; the app never guesses IDs or deletes unrelated sessions. Known session IDs remain in the durable cleanup retry table after case deletion. This uncertainty remains reported even when browser voice is explicitly enabled.

## Focused validation

`node --test scripts/setup-voice-agent.test.mjs` verifies dry-run isolation, both provider creation payloads, credential requirements, and safe errors. `vitest run --config apps/realtime/vitest.config.ts apps/realtime/tests/voice-agent.test.ts` exercises the production protocol in Workers, including a real local WebSocketPair upgrade, both LLM configuration gates, interruption, PCM boundaries, transcript/tool deduplication and logical deletion. All provider requests in those tests are mocked.

The historical opt-in `tests/browser/live.spec.ts` run used a real AssemblyAI session and the configured Nebius model with fictional Chrome microphone fixtures. It observed finalized transcription, evidence extraction, spoken agent audio and two-way human media after takeover. Physical two-device checks and a public deployment remain pending; [test results](test-results.md) separates those from automated evidence.

That historical Nebius evidence does not establish live compatibility of the optional AssemblyAI managed path. Keep any new provider verification tied to its own configuration, revision, and recorded result.
